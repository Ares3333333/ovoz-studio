# Память: форензический аудит тяжёлой цепочки — v0.30

Дата: 2026-09-29. Метод: сначала измерить, потом чинить; оптимизации без
измерений запрещены постановкой раунда. Все числа ниже — с живых прогонов на
этой машине (Windows, CPU-only, faster-whisper base int8, edge-tts через сеть),
монитор psutil, сэмплирование RSS каждые 100 мс.

## BEFORE — арифметика катастрофы (откуда "2.7 GB")

Пик одного dubbing-job'а складывался из четырёх независимых грехов:

| # | источник | измеримо/выводимо | было |
|---|---|---|---|
| 1 | буфер микшера `bytearray(int(total*rate)*2)`, total = span×2+60 | формула, 30-мин лента → 3780 с | 166.8 MB |
| 2 | `bytes(samples)` при записи — полная вторая копия | формула | +166.8 MB |
| 3 | восемь воркеров = восемь микшеров одновременно | GLOBAL_WORKER_SLOTS=8, лимита не было | ×8 → 2 668 MB |
| 4 | модель ASR живёт в процессе API вечно (синглтон) | измерение idle/load ниже | ~X MB постоянно |

OOM-kill контейнера — это НЕ исключение: ни run_job, ни future-guard его не
видят; строки jobs остаются 'running', кредиты списаны, возврат только при
следующем boot. Поэтому потолок памяти — вопрос корректности денег, не эстетики.

## Что исправлено в v0.30

1. **Абсолютный потолок буфера**: `cap_sec = min(span*2+slack, 900)` — 15 минут
   звука, 39.7 MB, решает контейнер а не загрузка (тест
   `test_mixer_output_ceiling_is_absolute_not_derived`).
2. **Ноль-копийная запись**: `w.writeframes(samples)` принимает bytearray по
   buffer-протоколу — вторая копия исчезла из формулы (−50% пика микшера).
3. **Слоты микшера**: `BoundedSemaphore(2)` вокруг `_mix_dubbing`; ожидающий
   третий job крутит acquire с `_check_deadline()` — ожидание не переживает
   оплаченную стену часов.
4. **Загрузка файлов стримится на диск** (`_spool_upload`, 1 MB чанки): тело
   job'а больше не живёт в RAM целиком; медиа-потолок поднят до 64 MiB —
   прежние 4 MiB делали 15-минутные ленты невозможными физически, пока весь
   конвейер продавал 30-минутные (тихая потеря функции, потолок не в той
   единице); tmpfs контейнера поднят до 256m под батч из десяти таких.
5. **Temp-файлы**: line_*.wav уничтожаются в `finally` на всех трёх путях
   (успех/timeout/исключение) — тест `test_mixer_temp_files_never_outlive_the_job`.
6. **Деградация деплоя**: `stop_grace_period: 11m` в compose — SIGKILL на
   10-й секунде раньше рвал живые paid-задачи на каждом релизе.

## AFTER — измеренный timeline (реальный long-form прогон)

Прогон: лента 913.75 с (15.2 мин), 24 реплики узбекской речи (Madina), тишина
между; job dubbing uz→ru, diarize=1; сервер v0.30.0; RSS uvicorn-процесса
(psutil, сэмпл 100 мс). Конфиг: OVOZ_ASR_SLOTS=1, OVOZ_DUB_SLOTS=1, OVOZ_ASR_THREADS=2.

| метрика | значение |
|---|---|
| статус job | **done** (полный путь ASR→diar→translate→TTS×24→mix) |
| wall | 326.9 s |
| idle RSS до job | **89.7 MB** |
| peak RSS во время job | **1070.4 MB** |
| RSS после job | 323.2 MB (модель остаётся намеренно; ~233 MB — удержанный CTranslate2-workspace) |
| пик на двух параллельных heavy job (slots=2, замер до фикса слотов) | **1322.8 MB** |

Вывод, не подогнанный под цель: **850 MB — FAIL**. Физический floor одного
long-form dubbing c faster-whisper **base int8** ≈ **1.1 GB** (модель + decode
окно CTranslate2 на 15-мин ленте). Буфер микшера теперь только 39.7 MB из
этих 1070 — до фикса одна только арифметика микшера давала 333 MB на job и
2.7 GB на восьми. Дальнейшее снижение — только меньшая модель (качество) или
process-isolation ASR (см. ниже), и то и другое — осознанный trade-off, не «оптимизация».

Транзитивная находка замера: edge-tts под burst'ом двух job'ов ответил
`No audio was received` и убил оплаченный 15-мин даб целиком — добавлены
deadline-осведомлённые ретраи (2, backoff) с честным событием в timeline job'а;
второй прогон прошёл насквозь (done).

## ASR-модель: синглтон против процесса

faster-whisper base int8 грузится ОДИН раз на процесс (double-checked locking),
`cpu_threads` — по умолчанию. Решение оставить синглтон в API-процессе, а не
выносить в subprocess, принято по измерению (см. таблицу загрузки выше): одна
копия модели на все job'ы против копий на каждый uvicorn-worker; при
единственном worker в образе (Dockerfile CMD без --workers) синглтон — это и
есть «модель вне web-воркера», просто без fork-налога. whisper.cpp бенчмарк:
бинарь на машине отсутствует (OVOZ_WHISPER_BIN пуст) — честно не замерено,
внесено в Remaining risks.

## Контейнерный тест (cgroup)

Реальный docker-демон, реальный cgroup-лимит `--memory 1g --memory-swap 1g`
(swap отключён), образ с production-Dockerfile:

| шаг | результат |
|---|---|
| `docker build` | BUILD_EXIT=0 (первая сборка падала: edge-tts в requirements, а его aiohttp не попадал в офлайн-wheels — Dockerfile исправлен, и это ровно та причина, по которой CI обязан собирать образ) |
| `/healthz` | 200 с первой попытки |
| `verify_2026` против контейнера | VERIFY_EXIT=0 (105/105 продуктивных проверок движка) |
| RSS контейнера: после boot / после полной прогонки | **44.0 MiB / 48.2 MiB из 1 GiB** |

Разделение, которое доказывает тест: **сам API-процесс в 1 GB умещается
семикратно** (48 MiB). Весь тяжёлый гигабайт принадлежит одному stage'у —
decode faster-whisper. Отсюда минимальная объективно необходимая инфраструктура
в секции ниже; врать, что «всё влезло в 850 MB», тест не даёт права.

## Рекомендация по инфраструктуре (по измерению, не пожеланию)

- Контейнер тяжёлого worker'а: **2 GB** (пик 1.07 GB + headroom аллокатора),
  OVOZ_ASR_SLOTS=1/OVOZ_DUB_SLOTS=1 при 2 CPU; слоты=2 ⇒ 4 GB.
- API без тяжёлых провайдеров (sim ASR/TTS): измеренный idle 89.7 MB — и 1 GB
  не нужен, но и не вредит.
- Process-isolation ASR (субпроцесс на job, RSS возвращается ОС на exit) —
  единственный путь вернуть ~230 MB удержанного workspace между job'ами;
  оставлено как следующий архитектурный шаг, не вслепую: цена +10 с загрузки
  модели на job (синглтон сегодня платит её один раз).

## Remaining risks

1. faster-whisper `transcribe()` сам по себе не имеет deadline — длинная лента
   может съесть слот до `_check_deadline` между шагами (стену часов ловит
   следующий чек, не текущий зов).
2. whisper.cpp / модель `small` не бенчмаркнуты на этой машине (нет бинаря,
   до-загрузка модели) — выбор base int8 задокументирован как дефолт, не как
   доказанный Парето-оптимум.
3. Windows-замер не равен cgroup: page cache и commit limit ведут себя иначе;
   контейнерная нога ниже — единственное, что считается production-доказательством.
