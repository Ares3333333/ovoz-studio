# Ovoz AI Studio — v0.22

Языковая AI-инфраструктура для Узбекистана и тюркских low-resource языков:
**субтитры, даббинг и перевод документов uz ↔ ru ↔ en** для креаторов, SME и мигрантов.

- `docs/ANALYSIS.md` — исследование рынка, заняты/свободны ниши, почему эта.
- `docs/ARCHITECTURE.md` — как устроено ядро (pipeline, billing, ling-слой).
- `docs/GTM.md` — план выхода на 1000 платящих за 90 дней.

## Быстрый старт

```bash
cd ovoz-studio
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8077
# открыть http://127.0.0.1:8077  (интерфейс UZ/RU/EN)
```

Демо-режим (по умолчанию) работает **полностью офлайн**: вместо «сырого» аудио
загружайте транскрипт `.txt`/`.srt` из папки `demo/` — весь пайплайн
(нормализация → перевод с глоссарием → SRT/ASS/WAV-даббинг → биллинг) отрабатывает честно.

## Собственный языковой движок — то, что нельзя скопировать (v0.11–v0.22)

Ядро продукта — проприетарный узбекский языковой слой `app/ling/`
(`romanizer` + `glossary` + `engine`). Ни один мировой продукт
(Descript / Veed / DeepL / Google) **не** делает узбекскую связку:

- **кириллица ↔ латиница** с учётом диграфов (shch/sh/ch, oʻ/gʻ) и **обратимый
  round-trip** без порчи уже готового текста (идемпотентность);
- **детект скрипта** с confidence и распознаванием mixed/code-switching;
- **официальный апостроф** по стандарту Oʻzbekiston 2019 (U+02BB `turned comma`)
  — вывод `oʻ`/`gʻ`, а не ASCII-костыль `o'`/`g'`;
- **защита брендов**: глоссарий применяется *после* транслитерации за один проход,
  поэтому названия не «плывут» при смене алфавита;
- сохранение регистра на уровне слова: `Шветсия→Shvetsiya`, но `Я ЛЮБЛЮ→YA LYUBLYU`;
- **конвертер реформы алфавита 2026**: 10 сентября 2026 Сенат Узбекистана одобрил
  новую латиницу (`Oʻ→Ö, Gʻ→Ğ, Sh→Ş, Ch→Ç`). До 2031 в стране сосуществуют ТРИ состояния
  письма — наш движок делает обратимый трёхсторонний перевод
  кириллица ↔ legacy-латиница ↔ новая латиница (`to=new_latin` в API, третья кнопка
  в живом виджете). Такого нет ни в одном продукте мира.

Движок открыт как **публичный, без-auth API** (и как интерактивный живой виджет на
лендинге — воронка роста):

```
POST /api/v1/ling/analyze        {text, terms?}                 → script, confidence, latin, cyrillic, official, метрики
POST /api/v1/ling/transliterate  {text, to, official?, terms?}  → результат транслитерации (to: latin | cyrillic | new_latin)
GET  /api/v1/ling/detect?text=                                   → классификация скрипта
```

Публичные эндпоинты защищены: скользящий rate-limit (60/мин/идентификатор), жёсткий
лимит тела запроса на уровне потока (включая chunked), cap на длину текста и число
terms, литеральные замены в глоссарии (без re шаблонизации) и kill-switch через
feature-flag `uzbek_language_engine` (fail-open).

### Ovoz Turn — разделение спикеров по смыслу (v0.12, `app/ling/diarize.py`)

Второй собственный движок: атрибуция спикеров на таймкодах. Pyannote/AssemblyAI
склеивают голоса по акустической близости и **теряют спикера, когда два голоса
звучат похоже** (телефон, диктофон, один микрофон). Ovoz Turn читает то, чего не
слышит акустика: структуру реплики, узбекскую морфологию и диалоговые правила.

- **четыре семейства улик**: structure (пауза, длина, обрыв фразы), morphology
  (лицо в глагольном суффиксе: `-siz/-san` против `-man/-miz`, вопросительное
  `-mi` **после** лица — `kelibsizmi` = 2-е лицо), dialogue (реплики-вопросы,
  обращение по имени, зеркальная пара приветствий `assalomu alaykum → va alaykum
  assalom`), voice (акустический профиль, если есть аудио);
- **fusion с потолком на семейство**: самая сильная улика весит полностью,
  вторая — 0.30. Поэтому набор слабых намёков не может «нарисовать» несуществующего
  спикера, а один сильный — не может быть перечёркнут шумом;
- **script-invariance**: одна и та же плёнка кириллицей и латиницей (включая
  реформу 2026) даёт **побайтово одинаковый** ответ — проверено тестом и live-
  проверкой; типографские признаки (заглавная в обращении) читаются на исходном
  тексте, потому что фолдинг их уничтожает;
- **никогда не выдумывает спикера**: монолог из 30 реплик остаётся одним голосом;
  `is_continuation` режет гиперсегментацию ASR, а полоса `W_ALTERNATE` передаёт
  слово другому **уже известному** голосу и не создаёт третьего;
- **объяснимость**: каждая граница несёт список улик и confidence — решение можно
  отладить и продать, а не только показать;
- **детерминизм**: чистый Python, без ML-моделей и без numpy — тот же вход даёт
  тот же выход в любом окружении, от ноутбука до Fly.io.

```
POST /api/v1/ling/diarize  {lines:[{start,end,text}]} | {srt:"…"}, max_speakers?≤8
                           → {speakers, turns, per_speaker, lines[{speaker,cues,confidence}], transcript}
```

В пайплайне включается флагом `diarize=1` на `/api/jobs` и `/api/jobs/batch` (и как
чекбокс в Studio), даёт артефакт `diarization` и теги `[S1]/[S2]` в transcript/SRT.
Ограничение честно: без аудио движок опирается только на текст и тайминг — там, где
два голоса говорят одинаковыми фразами и с одинаковыми паузами, он **оставит один
голос**, а не угадает.

### Ovoz Qator — вёрстка субтитров по нормам вещания (v0.13, `app/ling/layout.py`)

Третий собственный движок. Соседи — «кто сказал» (Ovoz Turn) и «что сказано»
(ASR + перевод) — не отвечают на единственный вопрос, который задаёт монтажер:
**успеет
ли зритель это прочитать**. Netflix/BCG-нормы (≤17 знаков/с, ≤42 знака в строке,
≤2 строки, ≥0.08 с зазора) публичны, но ни один продукт мира не применяет их к
узбекскому — а латинская/кириллическая узбекская строка заметно длиннее
английской при том же смысле, поэтому англоязычные пресеты здесь врют напрямую.

- **двигатель — закон чтения, а не «минимальная длительность»**: карточка получает
  `знаки / 17` секунд, и только потом вступает потолок `MAX_DWELL`. Поэтому
  переразметка не «красивая, но нечитаемая» — скорость ≤17 следует не из
  ограничения, а из физики времени на экране;
- **синхронность важнее читабельности**: два режима (`readability` занимает паузы
  и может уйти в дрейф, `sync` держит каждую карточку внутри её окна). Дрейф
  считается **внутри** сравниваемого отчёта: вариант на 3 с позже не может
  «выиграть» по баллу, потому что за опоздание снят балл. Решение принимается по
  закону, а не по спорному весу;
- **мера — правило, не пожелание**: перенос, который ставит на экран 43 знака,
  не выбирается даже если он «равнее». Если законного переноса внутри карточки нет
  вовсе — строка делится на две карточки, а не приезжает широкой: движок, который
  сам нарушает аудит, который продаёт, не имеет права на отчёт;
- **длительность округляется только вверх** (`_ms_up`) и ни одна проверка не
  округляется вниз: ложное срабатывание «17.0 знаков/с при лимите 17» на
  собственном выводе —
  это не точность, а потерянное доверие;
- **инварианты, а не впечатления**: ни одно слово не добавлено, не потеряно и не
  переставлено; карточки не перекрываются и не сливаются; атрибут спикера
  переживает разбиение реплики; чистый вход остаётся **на своих таймкодах**
  (переставить правильные субтитры — худшее, что может сделать «улучшатель»);
  детерминизм до миллисекунды;
- **честный отчёт**: каждое замечание несёт замер (`«24.4 chars/sec (max 17)»`),
  а не ярлык; балл 0–100 и оценка A–F; то, что движок не смог починить, остаётся
  в отчёте и стоит балла — клиенту не нужно гадать, ему показывают.

```
POST /api/v1/ling/layout  {lines:[{start,end,text}]} | {srt:"…"}, speakers?:[int]
                          → {before, after, cards[…], srt, mode, max_drift, in_sync, words_preserved}
```

Контракт отказа — часть обещания, а не деталь транспорта: реплика длиннее 300
символов **отвергается (422), а не обрезается**. Эндпоинт, продающий пословное
сохранение, не может тихо удалить хвост и потом вернуть `words_preserved: true` —
это уже правда о тексте, которого клиент не присылал. Отчёт закрывается и со
стороны чисел: `peak_cps` считается только по карточкам, где есть на что мерить,
а `cards[].cps` отдаёт `null` там, где времени на экране нет, — потому что
`Infinity` не является числом в JSON, а `layout.json` отдаётся клиенту как есть
(`response.json()` на share-странице умер бы на первом же таком артефакте).

В пайплайне — флаг `polish=1` (чекбокс «Ovoz Qator» в Studio, шаг 3.5 после
перевода): SRT отдаётся уже свёрстанным, рядом лежит артефакт `layout.json` с
отчётом «до → после», а двуязычная дорожка **сохраняет таймлайн ASR** — там и так
две строки на реплику, никакая вёрстка не сделает это читаемым, и трогать её
значило бы соврать в отчёте. Ограничение честно: если клиент даёт раздавленный
тайминг (130 знаков на 0.4 с), движок сохранит синхрон и доложит скорость, которую
не смог выполнить, — потому что опоздавший субтитр это неверный субтитр.

### Ovoz Jimlik — граница субтитра ставится в настоящую паузу (v0.14, `app/ling/align.py`)

Четвёртый собственный движок, и первый, который **слушает**. Три предыдущих работают
со знаком; этот отвечает на вопрос, который монтажер чувствует, но не может объяснить:
субтитр меняется посреди слова. ASR отдаёт таймкоды с ошибкой 0.2–0.5 с — он слышал
звук через модель и решал задачу распознавания; зритель в этот момент видит половину
слова на баре, который только что закрылся. Ни один продукт мира (включая облачные
«auto-align», которые просят WAV и возвращают тот же SRT) не делает этого для
узбекской речи — и не сделает по другой причине: пауза свойственна ленте, а не языку,
значит это нельзя привезти из переводческой модели.

- **закон, а не порог**: энергия считается 20-мс кадрами в децибелах, ворота
  ставятся между собственным шумом комнаты (`P10`) и уровнем речи (`P90`) и зажимаются
  с двух сторон — не ближе 6 дБ к шуму и не выше 12 дБ под речь. Гейт, посчитанный
  только от размаха распределения, попадал в межсложьевый провал и объявлял паузой
  согласный; такое «выравнивание» уносит границу **внутрь** слова, что хуже, чем ничего;
- **гистерезис (3 дБ) и две проверки на глухость**: `MIN_SPEECH_DB=-46` — «микрофон
  не подключён», `DYN_CAP_DB=40` — запас сверх 40 дБ это уже цифровой ноль. Лента
  без единой паузы (ровный тон) получает `moved: 0` и честное `no_pause_found`,
  а не выдуманные границы;
- **резание только внутри молчания**: граница притягивается в `[gaps.start+PAD,
  gaps.end−PAD] ∩ [t ± max_shift]`, `PAD=30 мс` — чтобы карточка не вспыхивала на
  краю слова. Ни одна граница не выходит за свою паузу и не уезжает дальше, чем
  разрешил клиент (`max_shift` — запрос, а не то, что движок вправе решить сам);
- **склейка идёт как одна граница**: `cue.end == next.start` — это один момент с
  двумя именами, и именно так пишет любой ASR и любой редактор. Если левое имя
  ограничить стартом соседа, который ещё не сдвинулся, граница не уедет никогда:
  ползёт только начало следующей строки, первая строка по-прежнему обрывается
  посреди слова, а между ними вспыхивает пустой экран. Поэтому общая граница
  считается по паре (не дальше `MAX_SPAN_LOSS` времени и не ближе `MIN_SPAN`
  дыхания к каждой из строк), а старт следующей реплики ограничивается снизу именно
  тем местом, куда приехала эта, — и оба имени оказываются на одной миллисекунде;
- **инварианты вместо впечатлений**: слова не меняются (у движка нет власти над
  текстом — поэтому реплика длиннее лимита **отвергается**, а не обрезается), порядок
  сохраняется, `MIN_SPAN=200 мс` не даёт карточке высохнуть, две карточки не делят
  кадр, суммарное перекрытие **не может вырасти** — это доказывается сравнением `до`
  и `после` в самом отчёте (`never_worse`), а не обещанием; уже правильные таймкоды
  не сдвигаются ни на миллисекунду;
- **отчёт — это замеры, а не ярлыки**: `moved / boundaries / in_silence /
  already_in_silence / max_applied / mean_applied / beyond_audio / no_pause_found /
  words_preserved / order_preserved / overlap_sec_before / overlap_sec_after`.
  `in_silence` — финальное состояние (сколько границ теперь сидит в молчании),
  `already_in_silence` — доказано, что ничего не трогали: слить их в один счётчик
  значило отдать клиенту `moved: 4, in_silence: 0` на четыре успешных перемещения,
  то есть «вы сдвинули четыре границы и ни одна не попала в паузу». Списки пауз и
  перемещений обрезаются по потолку (`gaps_truncated` / `moves_truncated`) и **говорят
  об этом**: отчёт, который тихо потерял хвост, — это не отчёт, а реклама;
- **граница доверия — заголовок WAV**: стандартный `wave` выводит ширину сэмпла из
  block-align и на 32-битном файле спокойно рапортовал `sampwidth=1`. Поэтому `fmt `
  разбирается вручную (формат ≠ 1 → «сжатый», bits ∉ {8,16} → «не та глубина»,
  противоречие block-align каналам и глубине → «ложный заголовок») и только потом
  сверяется с декодером: движок не имеет права строить тайминги на файле, который он
  неправильно прочитал.

```
POST /api/v1/ling/align  multipart: audio=<WAV 8/16-bit>, (srt:"…" | lines:[{start,end,text}]), max_shift?:сек
                         → {engine, audio{gaps,duration,…}, tuning, gaps[…], moves[…], cues[…], srt, summary}
```

Это единственный эндпоинт в семействе `ling`, который несёт запись, — и у него собственный
потолок тела (6 МБ против 130 КБ у JSON-маршрутов): 30 секунд 16-битного моно — это
~1 МБ, и байтовый бюджет JSON тут просто не та единица измерения. Потолок остаётся
маленьким намеренно, но теперь честно: он держит **память и очередь** анонимного
вызова, а не его CPU — огибающая считывает 5 МБ ленты за десятые доли секунды
(замеры — в «Окне прослушивания» ниже). Единицы не совпадают по обе стороны намеренно:
5 000 000 байт — это ~312 с ленты, то есть анонимный маршрут физически не может
дотянуться до окна движка в 900 с, а окно берегает читателя как библиотеку и как шаг
пайплайна. Отказ говорит о форме: 415 с именем
проблемы (`not_wav`, `compressed`, `bad_depth`, …) и `error_code: unsupported_media`
— 415 без собственного кода падал в `internal_error`, то есть говорил SDK'у «наша
вина, повтори» про файл клиента; 413 на слишком длинной ленте, 411 на загрузку без
объявленной длины (chunked-тело нельзя ограничить байтами до того, как оно легло на
диск), 422
на кривых репликах — причём реплики проверяются **до** буферизации загрузки, а
отказ всё равно сливает тело клиента в дренаж и закрывает сокет
(контракт v0.13).

В пайплайне — флаг `align=1` (чекбокс «Ovoz Jimlik» в Studio, шаг **1.6**: после
распознавания, до диаризации, перевода, вёрстки и озвучки). Порядок и есть фича: все,
кто работает по таймингам, получают уже исправленную карту, а не описывают timings,
которые вот-вот поменяются. Лента режется по **оплаченному** таймлайну (+60 с запаса)
до входа в движок — тогда «граница не могла уехать за конец аудио» автоматически
означает «не могла уехать за то, за что заплатили», и отдельный потолок после
выравнивания не нужен. Расшифровка ленты делается **один раз на задачу** и передаётся
обоим, кто слушает; два вызова ffmpeg были бы не только лишними часами, но и двумя
разными прочтениями одной записи. Без аудио шаг не молчит: в таймлайне появляется
`align: skipped: …`, а субтитры всё равно приходят. Витрина (`Ovoz Jimlik` на странице
языкового движка) не содержит записи: браузер сам синтезирует 5-секундную ленту —
три слога с межсловными провалами и шумом комнаты — и просит сервер её услышать,
потому что движок, проверяемый подставным образцом, ничего не доказывает. 70 тестов
(`tests/test_align.py`) собирают аудио из `math` и `array`: без numpy, без файлов,
без сети, детерминированно на любой машине; `scripts/probe_align_live.py` (16
проверок) прогоняет то же по живому сокету — дренаж тела при 413, `Connection: close`,
отказ по имени контейнера и побайтовая идентичность двух ответов.

### Ovoz So'z — у каждого слова своё время (v0.15, `app/ling/word.py`)

Пятый собственный движок и второй, который слушает. Jimlik ставит границу карточки
в паузу — но внутри карточки десять слов по-прежнему стоят под одним временем.
Слово просит заказчик: `\kf`-караоке для монтажа, follow-along чтение, нарезка по
отдельной фразе, вход для выравнивания TTS. Всё это в мире делают forced aligner'\ом,
обученным на размеченной речи, — поэтому для узбекского этого нет ни у кого: корпуса
нет. У этого движка модели тоже нет. Ему хватает двух вещей, которых нет у
транскрипта: какие кадры ленты являются речью (тот же Шмитт-гейт, что у Jimlik,
поэтому два слушателя не могут разойтись в показаниях об одной записи) и сколько
воздуха требует узбекское слово (кластеры гласных с учётом `ё/ю/я` и апострофа
`oʻ/gʻ`, плюс малый член за длину). Из этого строится скелет правдоподобных
границ, а **каждую из них решает лента**:

- **граница едет в настоящую просадку** внутри строки, через согласованное
  присваивание: порядок слов и порядок границ не могут пересечься, одна просадка не
  достаётся двум словам (жадное «ближайшее» ломалось именно на этом); где
  говорящий не оставил просадки — граница едет в самый тихий кадр рядом, и отчёт
  говорит, что именно произошло: `valley / quiet / speech` на каждый разрез;
- **текст не властен движку**: токены возвращаются байт-в-байт, ничего не
  добавляется и не теряется (текст копируется, а не пересобирается);
- **карточка делится, а не приближается**: первое слово начинается ровно там, где
  начинается карточка, последнее кончается ровно там, где она кончается, границы
  строго возрастают и непрерывны — подсветка не может встать на паузе или наложиться
  на соседнее слово (`longest_word_sec` и `min_word_sec = 60 мс` держат это числом);
- **неизмеримое отвергается, а не выдумывается**: карточка быстрее одного кадра на
  слово, лежащая за концом ленты или не влезающая в окно получает `reason`
  (`too_fast` с `cps_needed`, `outside_audio`, `too_short` с `frames/needs`) и не
  несёт слов, а весь остальной файл свои тайминги всё равно получает;
- **`valley_share` — измеримая честность**: доля границ, найденных лентой, а не
  геометрией. Ровный тон (межсложьевые провалы −6 дБ, которые гейт не считает
  молчанием) отвечает `0.0`, и проверка на это есть: движок, назвавший геометрию
  измерением, был бы пойман живым прогоном;
- **экспорт, который плеер понимает**: WebVTT с внутренними метками
  `<hh:mm:ss.mmm>` на каждое слово (браузерные `<track>` читают это нативно) и ASS
  с `\kf` в сантисекундах. Отвергнутая карточка не даёт ни строки: половина
  караоке-строки хуже, чем её отсутствие.

Транспорт у So'z тот же, что у Jimlik: одна multipart-коробка, один потолок тела
(6 МБ / 5 МБ на файл), одна таблица кодов отказа (`WordError` — наследник
`AlignError`, поэтому «плохой WAV» остаётся одним и тем же плохим WAV, какой бы
вопрос к нему ни задавали), и `too_many_words` считается **по тексту до первого
кадра**: восемь тысяч слов отказываются за 0.0 с, а не отсчитываются тридцать
секунд. Маршруты, несущие запись, перечислены одним списком `_LING_AUDIO_PATHS` —
новый слушатель, забытый в нём, получит JSON-потолок 130 КБ и честно отвергнет
каждую честную загрузку, то есть громко.

В пайплайне — флаг `words=1`, шаг **3.6**: после вёрстки, то есть слова считаются
по тем карточкам, которые уходят клиенту, а не по тем, которые потом переломятся.
Артефакты — `words.json` и `subs_karaoke.ass`; без аудиодорожки шаг не молчит
(`words: skipped: …`). Витрина (`Ovoz So'z` на странице движка) синтезирует ленту
**из самого списка реплик** — длительность слова по тому же закону гласных, 60 мс
воздуха между словами, — потому что живой QA поймал первый вариант витрины на
`0% настоящих просадок`: три ровных бука не содержат межсловной паузы, и честный
движок честно показывает в ней только геометрию. 78 тестов (`tests/test_words.py`)
на аудио из `tests/audio_studio.py` (без numpy, без файлов, без сети) плюс
`scripts/probe_words_live.py` (36–37 проверок по живому сокету — одна включается,
только когда 429 действительно случился: дренаж тела при лгущем
`Content-Length`, 8-бит и ложный тег сжатия, отказ без чтения кадров,
`too_fast` и `outside_audio` внутри 200-го ответа, лента длиннее прежнего потолка,
и вежливое переживание троттла 429 по `Retry-After`).

### Окно прослушивания — 900 секунд, и почему прореживание отклонено (v0.16)

До этой версии оба слушателя читали не больше `1 600 000` отсчётов, а пайплайн
декодировал 900 секунд ленты. На рабочей частоте (8 кГц) это 200 с против 900 с,
то есть **любая оплаченная задача длиннее трёх с половиной минут молча теряла
Jimlik и So'z**: шаг возвращал `skipped: too_long`, субтитры выходили, и ничего
не кричало. Потолок был выражен не той единицей — не лимитом оплаты, а размером
буфера, — и это не ограничение, а дыра в продукте.

Прежде чем чинить, измерили (`frame_levels`, чистая Python-петля, 8 кГц моно):

| длина ленты | каждый отсчёт каждого кадра | посимвольная скользящая сумма квадратов | кадры вразбивку (stride) |
|---|---|---|---|
| 200 с | **0,131 с** | 0,478 с | 0,135 с |
| 900 с | **0,596 с** | 2,376 с | 0,183 с |
| 1800 с | 1,291 с | 4,558 с | 0,212 с |

Точная огибающая пятнадцатиминутной ленты стоит полсекунды. Значит прежний
потолок отказывал задачам ради экономии, которой нет. Прореживание отклонено не
на словах, а по двум причинам: экономить там нечего (0,6 с — это не бюджет), а
платят за него точностью — выборка вразбивку читает ровный тон с периодом равным шагу
как конфетти (алиасинг решётки), склейка блоками лечит высокочастотную несущую, но
возвращает дрожание низкочастотной; а между словом и паузой лежит именно то
короткое, что и должно быть найдено. Скользящая сумма оказалась в 4 раза медленнее
прямого среза (значения совпадали — проверено), `audioop` (C-скорость) удалён из
3.13 и развил бы детерминизм между окружениями. Вывод зафиксирован тестом: пока
движок слушает, он читает **каждый** отсчёт, и в исходнике `frame_levels` не должно
появиться ни второго индекса, ни слова «stride».

Итог — один закон на обоих слушателей:

- `MAX_LISTEN_SEC = 900.0` — окно в **секундах**: сколько ленты слушатель держит
  в руках за один проход. С v0.22 это **не** потолок задачи (см. «Ovoz Qayta»
  ниже), а размер блока; для анонимного вызова он остаётся потолком, потому что
  анониму нельзя платить за час чужого декодирования;
- `MAX_LISTEN_SAMPLES = 9_600_000` — потолок **памяти** одного блока (те же 900 с,
  но до 16 кГц); два разных вопроса не могут решаться одним числом;
- `check_listen_window(n, rate, err=…)` — один закон для `align`, `word` и
  WAV-ридера, причём `pcm_from_wav` вызывает его **до** `readframes`: слишком
  длинная лента отвергается за доли секунды, а не после выделения буфера (есть
  тест с обманывающим заголовком `data` и границей в 0,5 с); `err` позволяет
  каждому слушателю отказать собственным классом, не разъходясь в числе;
- 413 анонимного маршрута отвечает **секундами**: «max 5000000: about 312s of 8 kHz
  mono 16-bit WAV; longer tape belongs in a job» — байты клиенту ничего не говорят,
  а «дальше — в задачу» это путь, которым он реально пользуется.

Флагманский регресс: 15-минутная лента (7 200 000 отсчётов, 300 карточек) —
**300/300** границ ушли в настоящую паузу, `max_applied = 0,18` с, последняя
карточка стоит на 896,03 с, отчёт конечен (список пауз обрезан счётчиком, а не
раздулся), и весь прогон занимает 0,645 с; у So'z на той же ленте
`cut_valley = 150 / valley_share = 1.0` — обещание «границу решает лента»
распространяется на пятнадцатую минуту так же, как на первую.

### Что нашёл внешний ревью этой же дельты (v0.16.2)

Поднять окно — значит заново посмотреть, что оно держало. Ревью дельты нашло
четыре вещи, и все четыре — последствия перенесённого потолка, а не опечатки:

- **Слушатели считали в event loop.** Маршруты `async def`, движки — чистый
  Python: один анонимный запрос на пятиминутную ленту останавливал `/healthz`,
  WS-хаб и весь API, пока читал кадр за кадром (до этого релиза работа была хоть
  чем-то ограничена — старым потолком в 200 с). Теперь `run_in_threadpool`, плюс
  `_LING_LISTENERS = BoundedSemaphore(2)`: третий одновременно пришедший
  слушатель получает `429` с `Retry-After: 5`, а не очередь, которая для клиента
  выглядит как зависание. Класс лимита для этих двух маршрутов — 12/мин против
  60/мин у текстовых: «разрешено» и «по карману» — разные вопросы.
- **8-битная ветка умножала память.** `array("h", [... for b in raw])`
  материализовал список из пяти миллионов указателей плюс столько же отдельных
  `PyLong` — порядка 190 МБ временного RSS на 5 МБ загрузки, и новое окно это
  пропускало. `array()` принимает генератор: арифметика та же, пика нет
  (тест сверяет каждый отсчёт с независимым пересчётом).
- **Потолок по байтам не существовал для chunked-тела.** Все отказы по размеру
  ключуются по `Content-Length`, а `Transfer-Encoding: chunked` его не
  объявляет — и Starlette успевает выложить тело во временный каталог до того,
  как мы ответим. Отсюда `411 Length Required` с `error_code: length_required`
  на маршруты, несущие запись (после дренажа ограниченного префикса, иначе
  отказ доходит до клиента как reset). Все реальные клиенты этого продукта —
  SPA, curl, urllib, пробы — длину объявляют, поэтому проверка ничего не ломает
  и проверяется живьём настоящим chunked-запросом.
- **Окно без зазора — это граница, а не потолок.** `DIAR_MAX_ANALYZE_SEC =
  int(MAX_LISTEN_SEC)` означало, что `ffmpeg -t 900` может выдать на кадр больше,
  чем движок соглашается прочитать, — и job, купленный ровно на окно, терял обе
  платные опции через `too_long`. `LISTEN_MARGIN_SEC = 5` держит декод строго
  внутри окна, и именно с окном декодера теперь сравнивается честная пометка в
  событии задачи (иначе она молчала бы ровно там, где и написана).

Плюс два места, где тест проверял не то: «heard 900s of 1200s» проверялся у
хелпера, но не в событии задачи (удаление `{note}` из обеих f-строк давало
зелёный набор), и гейт «огибающая читает каждый отсчёт» обходился прореживанием
*внутри* того же среза — теперь есть числовой контрпример: кадр, громкий только на
чётных отсчётах, не имеет права читаться как тишина.

### Отчёт движка на карточке задачи (v0.17)

До сих пор честность жила в API. Пайплайн писал в событие задачу фразу, а клиент
показывал зелёную пилюлю: заплатил человек за Jimlik и So'z или нет — на экране было
не видно. Выпрямить это можно было одним из двух плохих способов: напечатать
английскую строку лога (тот же класс дефекта, что и сырые `skipped: …` в ошибках)
или придумать фронтенду свою арифметику поверх текста. Выбрано третье: **у события
теперь два поля** — `message` для человека, который читает логи, и `data` для
клиента, который обязан говорить на языке клиента.

- **Схема v7** добавляет `job_events.data_json`; `add_job_event(..., data=…)`
  пишет его, `job_timeline()` читает обратно словарём. Строки, записанные до
  миграции, читаются как `{}` — история не падает и не выдумывает результат.
  Тот же `data` идёт живьём по WebSocket и в `progress` списка, чтобы карточке не
  нужно было ждать конца задачи;
- **Клиент собирает фразу из шаблона**, а не из прозы: `st_align_ok` —
  «{a}/{b} границ · макс. сдвиг {c} с · пауз {d}», `st_words_ok` — «слов: {a} на
  {b}/{c} карточках · настоящих просадок {d}%». `tf()` подставляет именованные
  токены, поэтому порядок слов в узбекском или русском — дело перевода, а не кода;
  гейт сверяет наборы `{токенов}` между всеми тремя локалями (потерянный токен —
  это фигурная скобка на витрине);
- **Обрезка по окну — отдельная строка** («услышано {a} с из {b} с · окно {c} с»):
  ровно тот случай, который раньше терялся молча, теперь называется на экране;
- **Отказ — не одно слово «skipped», а причина**: гейт берёт `_ALIGN_REFUSAL_STATUS`
  (таблица, из которой транспорт выбирает HTTP-статус) плюс статические причины
  пайплайна — 18 кодов — и требует фразу для каждого в uz/ru/en. Новый код отказа
  не сможет приехать к клиенту как `bad_rate` латиницей: CI покраснеет;
- **Чипы артефактов перестали показывать имена колонок**: `align`, `words`,
  `ass_karaoke` рендерились дословно («SOʻZ», «JIMLIK», «ASS ♪» теперь есть), и
  гейт вычитывает список прямо из `_JOB_ARTIFACT_KINDS`;
- **Раскрытие живёт по правилам дорогого интерфейса**: один запрос на задачу
  (список таймлайна не носит), состояние раскрытия переживает следующий repaint
  списка, переключение языка перерисовывает отчёт без сети, фокус возвращается
  кнопке после перерисовки (клавиатурный пользователь не улетает в начало
  страницы), а пустой отчёт честно говорится отдельной строкой, а не молчанием.

Живое доказательство: настоящая 60-секундная лента, загруженная через браузер,
дала на карточке «Выравнивание по тишине · границ в тишину: 1/4 · макс. сдвиг
0.03 с · пауз 20» и «Пословное время · слов: 15 на 2/2 карточках · настоящих
просадок 0%»; текстовый .srt дал «пропущено: нет аудиодорожки» — то есть отказ
объяснён, а не спрятан; переключение RU↔UZ перекрасило отчёт без единого запроса.

### Ovoz Nafis — право реза узбекского предложения (v0.18, `app/ling/nafis.py`)

Шестой собственный движок. Вопрос, на который он отвечает, — не «красиво ли выглядит
карточка» (это Qator) и не «когда говорить» (это Jimlik), а **разрешено ли вообще
резать здесь**. Для языка с постпозициями, составными глаголами и сказуемым в конце
ответ не выводится из ширины строк и баланса: разрез, правильный по 42 знакам,
неразбираем по-узбекски.

Сначала измерили, а не поверили на слово. Шесть реальных фраз интервью, тайминг
~19 знаков/сек (то есть вёрстка обязана резать), — 14 карточек, 13 границ между
ними. До движка: **1 разрез рвал словесную группу** (`tayyorlayotgan || bo'lsangiz` —
прогрессивная форма разрезана пополам), 6 границ приходились на середину клаузы.
После: **0 из 13 запрещённых разрезов**, пик скорости чтения и ни одно крупное
замечание аудита — не ухудшились. Доля разрезов внутри клаузы осталась прежней,
и это честно: закон запрещает рвать *группу слов*, а «вкус» места реза остаётся
dисконтом Qator, а не законом.

Пять законов, и каждое формулировка платит за неоднозначность языка:

- `postposition` — `uchun`/`bilan`/`haqida` не могут открывать карточку: они
  правят фразой слева. `keyin`/`so'ng`/`ichida` — та же форма и как наречие,
  поэтому обвиняются только когда предыдущее слово не кончает клаузу:
  «tekshirib, || keyin esa» — законно, «uch soat || keyin» — разрыв;
- `compound_verb` — `tayyorlab berdi`, `ko'rib chiqamiz`, `bo'lib bo'lmaydi`,
  `kelgan edi`: деепричастие и вспомогательный глагол — одно сказуемое;
- `bind_right` — `va`, `yoki`, `chunki`, `agar` не закрывают карточку: они
  обещают следующее;
- `pair` — `shuning uchun`, `garchi bo'lsa` — один союз, вынесенный по половинке
  в разные карточки, читается как два;
- `numeral_unit` — `yigirma || kishidan`, `ikki || oy`: число в отрыве от единицы
  измерения — классический машинный разрез.

Тесты за один прогон поймали два багонаписателя самого движка: `fold()` не
нормализовывал U+02BB (собственно узбекскую апострофу) — то есть все правила с
апострофом молча не срабатывали; и стем `bol` при `bo'ldi` — мёртвое правило
хуже отсутствия правила, потому что отчёт при нём остаётся зелёным. Теперь гейт
перебирает всю таблицу апострофов и требует, чтобы каждый стем был записан уже
свёрнутым.

Куда встроен: **один оракул в одной точке**. Все решения о разрыве в Qator (перенос
строки, разбиение карточки, смягчение границы) идут через `_break_cost`, поэтому
`nafis.penalty()` покрывает их все — и гейт следит, чтобы новый splitting-код не
смог выбрать разрыв в обход закона. Цена закона (260) сидит **между** балансом и
ценей ширины (400): широкую карточку не прочитать вообще, поэтому ширина по-прежнему
важнее грамматики. Отдельно зафиксировано, что `_CONNECTIVES` Qator — это вкус
(скидка), а законы Nafis — запрет: два списка держатся разными намеренно.

Живой зонд `probe_layout_live.py` получил проверку «ни одна граница не рвёт словесную
группу» — она судит ответ **работающего сервера** (21/21, cards=12, forbidden=0), а
не только импорт движка в тесте.

Пока честно об объёме: отдельного эндпоинта и виджета у Nafis ещё нет — движок
работает внутри вёрстки, то есть в каждой задаче с `polish=1`, и уже там защищает
текст клиента. Отдельный `/api/v1/ling/nafis` (диагностика «где нельзя резать» для
редакторов) и витрина на странице движка — следующий шаг.

### Линейка разрезов: `/api/v1/ling/nafis` и витрина (v0.19)

Шестой движок стал видимым. `POST /api/v1/ling/nafis` принимает и готовый файл
(`lines`/`srt` — тогда судятся **границы доставленных карточек**), и просто абзац
(`text` — тогда движок не выдумывает тайминги, а отвечает по позициям). Ответ
говорит и то, и другое отдельными числами: `cut_positions`, `legal_positions`,
`forbidden`, `legal_share`, `faults`/`by_code`, и конечный список `ruler` с
кодами на каждую запрещённую позицию.

На странице движка — **линейка разрезов**: тот же абзац узбекской прозы, где каждое
место возможного разрыва отмечено волосковой линией, а запрещённые — красным, с
названием закона на языке клиента (`число отделено от единицы измерения`,
`составной глагол разрезан пополам`, `союз обещает следующую строку`). Один запрос
на клик, повторный клик — одна перерисовка, переключение языка подписывает метки
из того же ответа **без нового запроса**.

Обе поверхности поймали по настоящему багу — не теоретических:

- **Счётчики говорили о разных вещах.** `forbidden` считал *нарушения законов*, а
  `legal_positions` — *позиции*; `shuning || uchun` нарушает два закона сразу, и
  «23 legal + 5 forbidden ≠ 28» выяснилось прямо на живом прогоне. Теперь
  `forbidden` — позиции, `fault_count` — нарушения, `by_code` — разбивка, и
  тождество `legal + forbidden == cut_positions` держат и тест, и живая проверка.
- **`ham` обвиняли в том, чего он не делает.** Живая линейка пометила разрез после
  «siz ham» как разорванный союз. В этом чтении `ham` закрывает именную группу
  («ты тоже»), то есть разрыв после него — обычный стык клаузы; другая форма
  (`ham X ham Y`) и правда тянет за собой. Угадывать здесь решили не: частица
  убрана из bind-right, мотив записан прямо в закон, а тест запрещает ей вернуться
  в оба списка.
  Запрещённых меток на демо-тексте стало 12 → 10 — движок стал меньше доносить.

Живьём на 0.19.0: **651 тест**, **verify_2026 103/103** (7 новых — про эндпоинт,
арифметику линейки, имена законов и сам виджет на отдаваемой странице),
`probe_layout_live` **21/21** с проверкой закона на ответе работающего сервера,
браузер: 64 отметки, 10 запрещённых, 84% разрешённых, 1 запрос на весь виджет,
RU↔UZ перекрашивается без сети, горизонтального переполнения нет, консоль чистая.

### Реальный ASR и честное «а смог ли он?» (v0.20)

Продукт выглядит готовым ровно до того момента, как выясняется, что он делает без
ключей. Здесь к этому моменту отнеслись серьёзно: `WhisperASR` умел один CLI, а
`get_asr()` **молча** возвращал симуляцию, если админ включил реальный ASR, а
бинарника нет. Задача при этом завершается «успешно», и человек платит за текст,
который никто не слышал. Теперь:

- **два диалекта вместо одного** — `openai/whisper` и `whisper.cpp` (`whisper-cli`):
  разные аргументы и разные JSON-ы (у cpp — миллисекунды в `offsets`, у openai —
  секунды в `start`/`end`). Перепутать их — значит молча получить тайминги в 1000 раз
  длиннее ленты, поэтому единицы названы в `parse()`, а не угадываются. Диалект
  определяется по имени бинарника и наличию `.bin`-модели, но явный
  `OVOZ_ASR_DIALECT` всегда важнее догадки;
- **`status()` у каждого этапа** (`asr`, `translate`, `tts`) — отделеляет заявленное
  от доказуемого: найден ли бинарник на PATH, существует ли файл модели, есть ли
  ключ (`key_present`, не значение), установлен ли `edge_tts`. Причина формулируется
  так, чтобы её можно было показать оператору: `OVOZ_ASR_PROVIDER=real without
  OVOZ_WHISPER_BIN`, `ASR binary 'whisper-cli' not found on PATH`.
  `GET /api/v1/info` отдаёт это в поле `providers` — и ничего секретного: ни значений
  ключей, ни путей вне конфигурации; а падение самого селф-чека не может унести
  эндпоинт: этап отвечает `mode: "unknown"` с текстом ошибки вместо 500;
- **демо-распознавание видно клиенту.** Пайплайн пишет в событие `asr` код
  `demo_transcript` и в `meta` задачи `asr_demo`/`asr_reason`, API отдаёт это в
  `job.engines`, а карточка задачи — янтарный чип «текст демо — реального ASR нет»
  с причиной в `title`. Грейать `[демо]`-префикс внутри субтитров нельзя: тест на
  это есть, и он же запрещает UI читать содержимое файла клиента, чтобы решить,
  настоящее ли в нём слово. Заодно честно различаются два случая: заглушка
  дорисовала текст с аудио-источника — демо; клиент сам принёс `.srt`/`.txt` — это
  его текст, и чипа нет.

Попутно live-QA поймало ещё одно: возвращшаяся вкладка показывала законченную
задачу как «в очереди». Скрытая вкладка режет таймеры до ~1/мин, а Mini App скрыт
всякий раз, когда пользователь открывает список чатов. Теперь на `visibilitychange`
(и `pageshow` для возврата из bfcache) идёт один `refreshAll()` + переподключение
сокета; проверка — прям в странице, с подменённым `document.hidden`.

И тест, который падал не от кода: `1500 сегментов быстрее 3 секунд` был планкой по
настенным часам на общей машине и падал от нагрузки. Теперь измеряется отношение
(в 5 раз больше входных данных — не более чем в 12 раз дольше: квадратичный
регресс ловится, загрузка CI — нет), и весь набор стабильно зелёный один прогон.

Живой зонд поймал и устаревшее обещание в себе: проверка троттла ждала
`X-RateLimit-Limit: 60`, а класс прослушивающих маршрутов — уже 12 (с v0.16.2).
Числа теперь принадлежат тесту
(`test_the_listening_routes_are_a_tighter_cost_class_than_the_text_ones`),
а зонд проверяет форму ответа — окно не хуже текстового, пауза выполнимая. Иначе
живой прогон спорит с политикой, а не с поведением: 37/37 он показал после того,
как перестал ожидать старую цифру.

### Telegram Mini App: «назад», виброотклик и диагностика без секретов (v0.21)

Mini App — это webview без браузерного интерфейса, и на Android системный «назад»
**закрывает приложение**, пока сама витрина не заявит `BackButton`. Теперь слой
стека построен на единственном факте, который у браузера уже есть: нативный
`<dialog>` вызывает `toggle` при открытии и закрытии (он не всплывает, но ловится
в capture-фазе), поэтому список «что сейчас поверх чего» ведёт сам DOM, а не
память разработчика — новый диалог появится в стеке, даже если про него забудут.
Одно нажатие закрывает диалог, второе выводит из студии на лендинг, дальше кнопка
гаснет. Проверено в живом браузере с подставным SDK: порядок, видимость и то, что
`toast()` порождает `HapticFeedback.notificationOccurred` — один канал обратной
связи вместо четырнадцати, которые можно забыть.

И второй, более досадный дефект: `tg.ready()` стоял **под** ранним `return` для
уже авторизованного пользователя — то есть самый частый гость Mini App никогда не
сообщал хосту, что страница готова. Теперь `ready()/expand()/тема/BackButton`
выполняются до любой ветки авторизации, и каждый вызов хоста обёрнут: не-Telegram
или старый SDK не должны ломать загрузку.

Третья мелочь той же природы: `telegram-web-app.js` загружается и в обычной вкладке
браузера — и там `BackButton`/`HapticFeedback` не поддерживаются, а SDK на каждый
вызов пишет `warn` в консоль, которая иначе была чиста. Mini App-поверхности
теперь заявляются только внутри Mini App (`tgInsideApp()`: не `web`-платформа,
не пустой `initData`), а проверка в живой вкладке подтвердила, что консоль снова
пустая — и что стек «назад» работает, когда вместо браузера подставлен клиент
(`platform: android`, два нажатия: диалог → лендинг → кнопка гаснет).

### Что нашёл security-ревью этой же линии (v0.21.1)

- **Полуправка CRITICAL из v0.16.2.** Аудио-маршруты были вынесены в threadpool и
  ограничены слотами, а `diarize`/`layout`/`nafis` остались считать в event loop —
  и их класс (60/мин) был *щедрее*, то есть именно дешёвый по идее класс мог
  положить `/healthz` для всех. Теперь все пять движков идут через `_ling_run()`
  (слот + пул + гарантированный release), у текстовых — три слота, ответ — `429`
  с `Retry-After`. Гейт перечисляет маршруты по имени, потому что «список, который
  надо помнить» и был причиной ошибки.
- **Бесплатный путь отказа.** Rate-limit стоял *после* веток 411/413, поэтому
  аноним мог жечь сокеты и дренаж бесконечно, ни разу не потратив бюджет. Теперь
  лимит проверяется первым и отказ тоже стоит токен; сломанный self-check этапа
  больше не уносит `/api/v1/info` — отвечает `mode: "unknown"`, а текст ошибки
  уходит в лог, не в публичный JSON.
- **Диагностика текла наружу.** v0.20 отдавал анониму имя бинарника, путь модели,
  `binary_found` (oracle: «такой файл на этом хосте есть») и классы исключений.
  Теперь у статуса два слоя: публичный `provider/mode/code/reason` (переменная
  окружения — это документация; её значение — это топология) и `operator`-половина
  только за админ-ключом в `/api/admin/status`. Чип «текст демо» в UI показывает
  причину без путей.
- **Наши же клиенты не слушали `Retry-After`.** Как только отказ стал стоить
  токена, живые зонды начали получать 429: `probe_align_live` сравнивал «два
  одинаковых ответа» и один из них был 429. Починено честно — зонды вежливые:
  ждут столько, сколько им сказано (это и есть контракт, который мы обещаем SDK).

### Модель безопасности v0.10 (13 раундов code-review + production hardening)

Аутентификация и сессии:

- Пароль/секрет пользователя — **PBKDF2-HMAC-SHA256** (120 000 итераций,
  16-байтная свежесгенерированная соль на каждого, self-describing `algo=pbkdf2_sha256$N`).
  Legacy-SHA-256 прозрачно мигрируется на первом входе.
- **Секрет обязателен при регистрации** (min 10 символов). Пустой/короткий — 422.
- Login возвращает **единый 401** для «нет контакта», «нет секрета» и «неверный секрет» —
  оракул перечисления закрыт.
- Session TTL = 30 дней, sliding extend раз в час; `/api/auth/logout` отзывает токен.
- Rate limit: 8 неудач за 15 мин на пару (контакт, IP) → 429 с `Retry-After`.
  Второй контур — на регистрации и TG-auth по IP.
- Нормализация контакта (E.164-lite для телефона, lowercase для email): 3 формата
  одного номера = один аккаунт, farming бонусов блокируется.

Транспорт и HTTP:

- Токен принимается **только в `Authorization: Bearer`** (case-insensitive per RFC 7235) или `X-API-Key: ovoz_…` (programmatic).
- Security-заголовки на всех ответах: CSP (`worker-src`, `upgrade-insecure-requests`),
  `X-Frame-Options: DENY`, `COOP: same-origin`, `CORP: same-origin`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`, `X-Response-Time`, `X-Request-Id`.
- `script-src` **без** `'unsafe-inline'` и без `'unsafe-eval'`: в документе нет ни одного
  inline-`<script>` и ни одного `on*`-атрибута (загрузчик Telegram вынесен в
  `static/tg-boot.js`, регистрация SW — в `static/sw-boot.js`), и инвариант-тесты не
  дадут вернуть их обратно. Injected `<script>` из stored XSS не выполняется, а
  блокируется; `style-src 'unsafe-inline'` остаётся осознанно (inline-стили плеера).
- `/healthz` возвращает `{ok, version, db, circuits}` — deep health с circuit state.
- `/metrics` — Prometheus text-format (uptime, active/total jobs, sessions, workers).
- Structured error envelope: `{detail, error_code}` — machine-readable codes.
- Отказ **читаем**: 413 по размеру тела сначала дослушает тело клиента (drop, не
  buffer, потолок `лимит + 1 МБ` и 3 с), и только потом отвечает. Без этого сокет
  рвался на середине, SDK получал `connection reset`, и обещанный structured error
  не доходил ни до одного клиента, который переслал лишний килобайт (найдено живым
  прогоном `scripts/probe_layout_live.py`, не юнитами).

Биллинг и платежи:

- Цену задачи считает **только сервер** (ffprobe для аудио, SRT-тайминги/слова для текста).
- Webhook ПС: HMAC-SHA256 подпись обязательна; без `OVOZ_WEBHOOK_SECRET` эндпоинт 501.
  Сумма, не совпадающая ни с одним тарифом, отклоняется **422** и не начисляет ничего
  (раньше silently ресайзился до 600 мин — дыра закрыта).
- Списание атомарное (`INSERT … SELECT WHERE balance ≥ x`); двойной возврат исключён
  CAS-переходами статусов (возврат делает только победитель гонки cancel/fail/restart).
- После рестарта сервера «сиротские» queued/running jobs помечаются failed с возвратом.

Защита ресурсов:

- Content-Length middleware pre-check (BEFORE body parse) + `MAX_UPLOAD_BYTES` (4 МБ)
  + magic-byte validation for audio/video + чистка осиротевших файлов.
- **Timeline clamp**: сегменты дальше оплаченного таймлайна + 60 с вырезаются.
- **Segment cap**: 1500 сегментов max (защита от DoS через большой .srt).
- **Wall-clock timeout**: 600s per job, enforced before/during ASR, between translate chunks.
- **Circuit breaker** per provider: 5 consecutive failures → OPEN for 60s.
- Пул воркеров: `ThreadPoolExecutor(8)`; per-user cap активных задач = 5.
- Глоссарий: ≤200 терминов на запрос, ≤128 символов на термин, ≤500 на пользователя.
- Retention cleanup thread: purges finished jobs + files older than `OVOZ_RETENTION_DAYS`.

Telegram Mini App:

- initData проверяется официальным HMAC-алгоритмом; `auth_date` из будущего и старше
  6 часов отклоняются; single-use guard по `(tg_id, auth_date)` — одна выданная
  строка не превращается в 48-часовой bearer.

### Ovoz Qayta: слушать всю ленту, а не её первые пятнадцать минут (v0.22)

До этой версии потолок задачи назывался окном движка. Задача на 20 минут
получала выравнивание первых 895 с, галочку «готово» и ни строчки о том, что
остаток ленты никто не слушал; честная заметка появилась в v0.19, но заметка —
не результат. Причина была не в точности, а в форме памяти: `frame_curve` хотел
весь PCM одним объектом, а час 8 кГц моно — это 57 МБ целых чисел.

Смотрим, чем движки на самом деле питаются. `align` после `detect_gaps` не
касается отсчётов вообще: ему нужны кадры (50 чисел в секунду) и список пауз.
`word` — то же самое плюс пики речи. Значит ленту длиннее окна можно **слушать в
блоки**, а решать по одному глобальному отчёту:

- `Envelope(rate, block_sec)` — точный проход по блокам: неполный кадр
  переносится в следующий блок, поэтому последовательность кадров не зависит от
  того, где читатель остановился. Проверено на размерах 1 000 / 3 999 / 8 000 /
  8 001 / 16 000 / 480 000 отсчётов и на обрывающем байт (`levels`, `gate_db`,
  `duration` совпадают с одиночным проходом дословно);
- `block_sec` — обещание, а не комментарий: блок больше обещанного окна
  отвергается кодом `bad_block`, иначе «потолок памяти» снова станет текстом в
  docstring; `peak_samples` в отчёте — измеренный пик, а не оценка;
- **один алгоритм, а не два**: `align()` = `check_listen_window` + `align_curve`,
  `align_blocks()` = `Envelope` + тот же `align_curve`. Тест сверяет оба отчёта
  целиком, кроме блока `audio`, где и написано, как ленту слушали (`streamed`,
  `blocks`, `heard_sec`). Называть это скользящим окном было бы неточно: куски не
  пересекаются и не сшиваются, кривая одна на всю ленту, а значит и порог тишины
  один — первая и двадцатая минута меряются по одной комнате;
- потолок теперь выражает **оплата**: `min(оплачено + запас, MAX_JOB_TAPE_SEC)`,
  где `MAX_JOB_TAPE_SEC = 3600` — час. Он про CPU и память, а не про то, чего
  движок не хочет слышать; всё, что не влезло, по-прежнему называется числами
  (`heard_sec / paid_sec / window_sec`), и это редкий случай, а не штатный.

Плата за час — не только декод. `snap_one` на каждой границе перебирал **все**
паузы: 1500 карточек × десятки тысяч пауз — это тот O(n·m), из-за которого длинную
ленту и считали неподъёмной. Появляется `_GapIndex` (два `bisect` по списку пауз) и тот
же индекс для проверки «карточка не утонула в одной паузе». Детерминизм
оптимизации доказан, а не заявлен: 30 случайных наборов пауз × 60 вопросов —
индексный ответ байт в байт равен перебору, а список, который не является
возрастающим и непересекающимся, индекса не получает вовсе (падает на честный
перебор).

Один проход теперь обслуживает и диаризацию: `_SpanBook` забирает из потока
только окна профилей (до 4 × 1 с на карточку), закрывает их по мере прохода и
хранит три числа, а не ленту. Побочный, но важный итог: прежняя `_voices`
обрезала окно через `min(len(pcm), …)` и молча строила профиль из огрызка, если
карточка уехала за конец записи. Теперь такое окно засчитывается в `off_tape`, и
число едет в событие задачи (`code: turns`, `heard_sec`, `off_tape`) — карточка
произносит это на трёх языках вместо «1 голос / 2 реплики», где ноль не было
видно.

Живой прогон (`scripts/probe_reach_live.py`, 16 проверок): на сервер поднимается
реальная 16-минутная запись (MP3 3,84 МБ, 32 кбит/с моно, сгенерирована тем же
законом «две фразы и две настоящие паузы на каждые 6 с»), задача проходит за
2 с, и события задачи говорят: `duration = 960,0` (предел прошлой версии — 895),
`blocks = 16` при `block_sec = 60`, `streamed = true`, `heard_sec = 960,0`,
`never_worse = true`, `words_preserved = true`, `truncation` отсутствует, у So'z
та же кривая (16 блоков), у диаризации `off_tape = 0`. Оговорка к цифрам: демо-ASR
на этой ленте выдаёт две карточки, поэтому «переставлено 1» — это достижимость,
а не количество работы; число перестановок на ленте из 300 карточек измерено
тестом (`test_a_cut_at_minute_nineteen_lands_on_a_real_pause` и флагманский
регресс выше).

Что это запрещает на будущее: прореживание (отклонено измерением в v0.16),
склейку результатов перекрывающихся окон (порог тишины стал бы зависеть от
границы блока) и второй проход по ленте ради профилей (`_pcm` остался только для
тестов и крошечных фикстур — у живого job'а один decode, и это проверяется
гейтом). Тесты: 702, живой контроль: `verify_2026` 105/105, пробы 18/18,
37/37, 21/21 и reach-проба 16/16.

## Жизненный цикл задачи

`queued → running → done | failed | canceled` — каждый переход атомарен;
`retry` возможен только из failed/canceled (с повторным списанием),
`cancel` — только пока задача в очереди (с возвратом минут).
Хронология — в `GET /api/jobs/{id}` (timeline).
**WebSocket** `/ws/jobs?ticket=…` — push-events прогресса вместо polling: клиент
обменивает bearer на `POST /api/auth/ws-ticket` (одноразовый билет, 15 с) — сессия
никогда не ездит в query string, которую копируют access-логи. Один hub на юзера
(лимит сокетов), cross-thread публикация через `call_soon_threadsafe`, при обрыве —
автовозврат к поллингу с backoff.
**Pagination** `GET /api/jobs?cursor=<b64>&limit=20` — keyset cursor.
**Filters** `GET /api/jobs?status=done&jtype=subtitles` — server-side filtering.
**Sharing** `POST /api/jobs/{id}/share` — time-limited public artifact links.

## Per-endpoint rate limiting (v0.9)

Sliding-window (60 s) limiter in the HTTP middleware, keyed by **identity** (SHA-256 of
`Authorization`/`X-API-Key`, else client IP) and **rate-class** (matched route prefix, so
`/api/jobs/{id}/…` variants share one bucket — no per-id bypass). Limits: `/api/auth/*` 20/min,
`/api/jobs*` 60/min, `/api/glossary` 120/min, `/api/account/export` 6/min, `/api/admin/*` 30/min,
default 300/min. Bounded LRU (20 000 keys). 429 + `Retry-After` + `X-RateLimit-*`. Toggle via
`OVOZ_ENDPOINT_RATE_LIMIT` (default on). **A refusal spends the budget too**: the limiter is
the first thing in the middleware, so a client churning 411/413 drains its own allowance
instead of costing the server a drain per request for free. The two listening routes are a
different cost class (12/min, and `429 language listeners are busy` answered before the
multipart is parsed); the text engines get three worker slots of their own.

## Надёжность клиента и релизный контракт (v0.12)

Каждый пункт ниже — это отловленный в browser-QA баг, зафиксированный тестом:

- **Релиз доходит целиком.** `app/__init__.py`, `sw.js` (`BUILD`) и `?v=` в
  `index.html` штампуются одним `python scripts/bump_version.py <версия>`;
  lockstep держат тесты. Service Worker отдаёт код **network-first** (кэш — только
  аварийный офлайн-путь), а `?v=` меняет сам ключ кэша: иначе переходящая
  навигация обслуживается старым SW и пользователь получает вчерашний `i18n.js`
  рядом с сегодняшним `app.js`.
- **Документ — это манифест сборки, и он не имеет права стареть.** `StaticFiles`
  выдаёт ему только `ETag`/`Last-Modified`, а браузер без `Cache-Control`
  придумывает свежесть сам: 10% от возраста файла, то есть в Docker — 10% от
  возраста образа. Живой QA это и поймал: вкладка с `?v=0.15.2` поверх сервера
  `0.16.0` (выглядит как сломанный SW, им не являясь). Теперь `/` и любой
  `.html` идут с `no-cache`, а все код-файлы, которые перечисляет документ,
  — с `max-age=0, must-revalidate` (политика по суффиксам, а не по рукописному
  списку: `tg-boot.js`, `sw-boot.js` и манифест из того списка просто выпадали).
  Активируясь, воркер сообщает `build:<версия>` открытым страницам, и страница
  перезагружается **только** если её собственный штамп другой, один раз за сессию
  (`sessionStorage`-запор: иначе устаревший документ рядом со свежим воркером —
  это цикл перезагрузок).
- **Один запрос на событие.** `refreshJobs()` — дедупликация in-flight + один
  хвостовой refresh; `refreshAll()` — один проход на сессию; повторный вход в
  уже открытый studio не перечитывает всё. Отправленная задача рисуется из ответа
  POST (OPTIMISTIC), а не из перечитывания списка.
- **Ответ не красит чужую сессию.** `_sessionGen` в `_fetchJobs`: ответ,
  запрошенный до logout/login, выбрасывается, а не домалёвывается в список.
- **Порядок загрузки (TDZ).** Автологин Telegram — последние строки `app.js`:
  ни одного module-level `let/const` ниже точки входа. Иначе `let` ещё не
  инициализирован, `ReferenceError` тонет в async-цепочке, и студия после F5
  слепая: пустой список, ни сокета, ни поллинга, ноль сообщений в консоли.
- **Тихий отказ запрещён.** Фоновые refresh-и пишут `console.error`, а не `catch {}`:
  именно пустой catch сделал предыдущий баг невидимым.
- **Деньги и статусы по-человечески.** `fmtMinutes()` убирает двоичный шум
  (`4.430000000000001 min`); `job.error` локализуется префиксами
  (`job exceeded`, `worker restart`), машинная проза остаётся только в `title`;
  завершённая задача не держит замерший прогресс-бар.
- **Live-канал не портит фильтр:** `adoptJob` уважает активный фильтр, но
  помнит статус, чтобы готовое уведомление и aria-live не потерялись.

## Ограничения честно

- Слушание ленты — **один проход по блокам** (`Envelope`), а потолок задачи —
  оплата, ограниченная `MAX_JOB_TAPE_SEC = 3600` (час). Лента длиннее часа
  получает выравнивание первых 60 минут и честное «heard 3600s of 7200s» —
  событие, а не тихую разницу. Для анонимного `/api/v1/ling/{align,words}`
  закон прежний: окно 900 с и байтовый потолок 5 МБ (~312 с 8 кГц моно), 413
  называет и байты, и секунды, и путь «дальше — в задачу». Прореживание
  отклонено замером: огибающая читается по **каждому** отсчёту (см. «Окно
  прослушивания» и «Ovoz Qayta»).
- Точность слушания не зависит от того, сколько ленту слушают: 44,1 кГц стерео
  даёт ~109 с на те же 900 с окна, потому что потолок в отсчётах — на каналы;
  задача декодируется в 8 кГц моно, и это единственный случай, где частота
  уменьшается намеренно (голосу хватает, диаризации хватает).
- Подкаст длиннее часа получает выравнивание первых 60 минут и событие «heard
  3600s of 7200s»: потолок теперь про CPU и память одного job'а, а не про то,
  чего движок не хочет слышать. Поднять — вопрос одной константы и замеров, не
  архитектуры.
- Узкое место длинной ленты теперь не слушание, а текст: демо-ASR даёт несколько
  карточек на всю запись, поэтому на живой 16-минутной ленте переставляется одна
  граница. С реальным ASR карточки на всю ленту — то же самое слушание, без
  перестройки движка.
- Демо-переводчик словарный — качество даёт LLM/модуль, подключаемый ключом.
- Лимит загрузки 4 МБ; продакшн — object storage + очередь воркеров.
- Логи: `uvicorn` default. Для prod — `structlog` + `audit_log` таблица (login fail,
  webhook receipt, demo-credit, refund).
- Реальные платежи — после регистрации Payme/Click (нужны договоры, ИП/IT Park).
- Rate-limit живёт в памяти процесса: ок для одной реплики, требует Redis при scale-out.
